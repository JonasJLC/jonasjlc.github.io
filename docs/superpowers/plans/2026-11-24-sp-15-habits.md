# Strandparken Idé 15: Vaner i Sundhed — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A calm habit tracker inside Sundhed. A "Data" | "Vaner" switch at the top, personal and shared habits, manual habits ticked by hand, automatic habits that complete themselves from health data, weekly progress (never streaks that reset), a weekday ring row, a create sheet, and history with edit and archive.

**Architecture:** Two tables, `sp_habits` and `sp_habit_completions`, with row-level security and triggers that make the rules hold in the database. A person cannot write another person's personal habit, nobody can tick an automatic habit by hand, and `source = 'automatic'` can only come from the service role. All counting (week targets, "x af y denne uge", dots, today's "2 af 6 i dag", day rings, weeks in a row) is pure code in `lib/habits/model.ts`, tested exhaustively, with weeks as ISO weeks in Europe/Copenhagen (D53, `lib/madplan/dates.ts`). Automatic habits are evaluated by idea 10's `health-sync` after each upsert, so they work in the background too. The client shows automatic values only when the health metric is visible to the viewer (`sp_health_for`). Colours are a soft palette of `--sp-habit-*` tokens in `strandparken.css`. Manual habits can ship before idea 10. Automatic habits are switched on when idea 10 is live.

**Source:** `docs/app_ideer_-_strandparken_rettet.docx`, Idé 15. Mockups: image7.png (habit list), image8.png (list variant and the "Ny vane" sheet); reference screenshots image9.png and image10.png (style inspiration only, not to copy).

**Supersedes:** main spec §5.7 (habits), D17 (refined), D45 (frequency gains "bestemte dage" and automatic tracking; "no streak mechanics" kept in spirit, roadmap Q4), §5.6 item 4 (habits leave Hjem), slice 4.2, §6 row `sp_habits` / `sp_habit_logs`. Reminders: roadmap Q5 (stored and shown only).

## Data changes

Migration `…_strandparken_habits.sql` (sketch):

```sql
create table public.sp_habits (
  id uuid primary key default gen_random_uuid(),
  household_id uuid not null references public.households (id) on delete cascade,
  owner text not null check (owner in ('a', 'b', 'both')),          -- 'both' = Fælles
  title text not null check (length(btrim(title)) between 1 and 80),
  tracking text not null default 'manual' check (tracking in ('manual', 'automatic')),
  frequency text not null default 'daily' check (frequency in ('daily', 'per_week', 'weekdays')),
  per_week_count smallint check (per_week_count between 1 and 7),
  weekdays smallint[] check (weekdays <@ array[1,2,3,4,5,6,7]::smallint[]),   -- ISO, 1 = Monday
  reminder_time time,                                                -- stored and shown only (roadmap Q5)
  color text not null default 'sage' check (color in ('sage','moss','sky','lavender','plum','rose','clay','sand')),
  icon text check (length(icon) <= 16),                              -- an emoji or a lucide icon key
  rule jsonb,                                                        -- {metric, op, threshold}
  archived_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  created_by uuid references auth.users (id) on delete set null,
  unique (id, household_id),
  constraint sp_habits_frequency check (
    (frequency = 'daily' and per_week_count is null and weekdays is null) or
    (frequency = 'per_week' and per_week_count is not null and weekdays is null) or
    (frequency = 'weekdays' and cardinality(weekdays) between 1 and 7 and per_week_count is null)),
  constraint sp_habits_rule check (
    (tracking = 'manual' and rule is null) or
    (tracking = 'automatic' and rule ->> 'metric' in ('steps', 'sleep_score', 'activity_progress')
       and rule ->> 'op' in ('>=', '>') and jsonb_typeof(rule -> 'threshold') = 'number'))
);

create table public.sp_habit_completions (
  id uuid primary key default gen_random_uuid(),
  household_id uuid not null,
  habit_id uuid not null,
  date date not null,
  completed_by text not null check (completed_by in ('a', 'b')),
  source text not null default 'manual' check (source in ('manual', 'automatic')),
  created_at timestamptz not null default now(),
  unique (habit_id, date),
  foreign key (habit_id, household_id) references public.sp_habits (id, household_id) on delete cascade
);
```

**Policies** (`authenticated`; the service role bypasses RLS):

- `sp_habits`: members read all habits in their household (main spec §2.1: the other person's personal habits are readable; the UI only shows Mine and Fælles). Insert, update and delete are allowed when `owner = 'both'`, or when `owner` equals the caller's `household_members.person`. `owner` cannot change on update (trigger keeps `old.owner`), so a habit cannot be handed to someone else to edit.
- `sp_habit_completions`: members read all. Insert and delete are allowed only when the habit is in the caller's household and is `owner = 'both'` or the caller's own. A `before insert` trigger sets `completed_by` from the caller's person key, forces `source = 'manual'` when `auth.uid()` is not null, and raises `P0001` if the habit is `tracking = 'automatic'`. Delete is refused for `source = 'automatic'` rows. Dates more than 1 day in the future are refused.
- Realtime: `replica identity full` on both and add them to `supabase_realtime`.

**Policy test cases:** Jonas cannot insert, update or delete Camilla's personal habit, or tick it; either member can tick and undo a Fælles habit; ticking an automatic habit fails (`P0001`); a client insert with `source = 'automatic'` is stored as `manual` (or refused for automatic habits); `completed_by` cannot be spoofed; a non-member reads nothing; `owner` cannot be changed by update; deleting a habit cascades its completions.

## Tasks

### Task 1: Week logic (TDD)

`tests/strandparken-habits.test.ts` first. `lib/habits/model.ts`:

```ts
export type Owner = 'a' | 'b' | 'both';
export type Frequency = { kind: 'daily' } | { kind: 'per_week'; count: number } | { kind: 'weekdays'; days: number[] };
export type Rule = { metric: 'steps' | 'sleep_score' | 'activity_progress'; op: '>=' | '>'; threshold: number };
export interface Habit { id: string; owner: Owner; title: string; tracking: 'manual' | 'automatic'; frequency: Frequency; rule: Rule | null; color: HabitColor; icon: string | null; reminderTime: string | null; archivedAt: string | null; createdAt: string }
export interface Completion { habitId: string; date: string; completedBy: 'a' | 'b'; source: 'manual' | 'automatic' }
```

- [ ] `weekTarget(habit)`: daily → 7, per_week → N, weekdays → number of days. A habit created mid-week still targets the whole week (no penalty is shown either way).
- [ ] `isDueOn(habit, date)`: daily → every day; weekdays → only those ISO days; per_week → never "due" on a specific day (it counts only when done).
- [ ] `weekProgress(habit, completions, monday)` → `{ done, target, dots: boolean[] }`. Dots: `target` dots, filled from the left by completions this week (the mockup fills left to right, not by weekday). Completions above the target still count as done = target in dots; the text shows the true count ("8 af 7" is capped to "7 af 7").
- [ ] `detailLine(habit, progress, todayValue)`: "Hver dag · 3 af 7 denne uge", "3 gange om ugen · 1 af 3 denne uge", "Man, ons, fre · 2 af 3 denne uge"; automatic with a visible value: "82 i nat · 5 af 7 denne uge", "6.420 i dag · 2 af 5 denne uge"; automatic with the value hidden from the viewer: "Automatisk · 2 af 5 denne uge".
- [ ] `todayCount(habits, completions, today, filter)` → "2 af 6 i dag": the denominator is habits due today plus per-week habits not yet at target this week; the numerator is those completed today.
- [ ] `dayRing(habits, completions, date)` → 0–1: completed ÷ due on that date (per-week habits add to both sides only when completed that day). No habits due → `null` (an empty ring, never red). Future days → `null`.
- [ ] `weeksInARow(habit, completions, today)` → the number of consecutive full weeks with target met, ending last week (plus this week once met). It returns 0 without any "lost" state; the UI shows nothing below 2 (roadmap Q4).
- [ ] Shared habits: done when either member completes; `doneBy(habit, completions, date)` returns the person for "· Jonas" on the card.
- [ ] Archived habits are excluded from today's counts and rings, but kept in history.
- [ ] Copenhagen dates throughout; include a test across the DST change (29 March) and a week across the new year (ISO week 1).
