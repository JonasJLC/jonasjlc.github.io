# Strandparken Idé 5: To-do-liste under Lister — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the To-do segment of Lister: a shared list of one-off to-dos with an owner (Camilla, Jonas or Fælles), an optional due date and an optional note. It has quick add, an edit sheet, filter chips, the groups "Snart", "Når der er tid" and "Klaret", check-off in the list, swipe to delete with "Fortryd", and live sync between both phones.

**Architecture:** One new table, `sp_todos`, with the household policy shape every `sp_` table uses and full replica identity for Realtime, as `sp_shopping_items` has. The data code follows the existing per-feature layout: `lib/todo/model.ts` (pure grouping, filtering, overdue and validation, Node-tested), `lib/todo/repo.ts` (Supabase calls) and `lib/todo/use-todos.ts` (load plus `subscribeHousehold` for live updates). The screen is `lister/TodoView.tsx` inside Lister's To-do panel, with `lister/TodoSheet.tsx` for editing. Swipe uses `motion`'s horizontal drag, which is already a dependency. Every swipe action also has a button, so the list works without gestures.

**Source:** `docs/app_ideer_-_strandparken_rettet.docx`, Idé 5. Mockup: the two-screen image with "Hjem" and "Lister › To-do". **The text wins over the mockup** (roadmap Q3): the chips are Camilla, Jonas, Fælles (not "Alle, Mine, Jonas, Fælles"), and to-dos are **not** shown on Hjem.

## Data changes

`supabase/migrations/20261127090000_strandparken_todos.sql`:

```sql
-- Idé 5: one-off to-dos for the household. No recurrence. Owner is a person key or both.
create table public.sp_todos (
  id uuid primary key default gen_random_uuid(),
  household_id uuid not null references public.households (id) on delete cascade,
  title text not null check (length(btrim(title)) between 1 and 200),
  owner text not null default 'both' check (owner in ('a', 'b', 'both')),
  due_date date,
  note text check (note is null or length(note) <= 1000),
  completed_at timestamptz,
  completed_by uuid references auth.users (id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  created_by uuid references auth.users (id) on delete set null,
  constraint sp_todos_completed_pair check ((completed_at is null) = (completed_by is null))
);
create index sp_todos_household_idx on public.sp_todos (household_id, completed_at);

alter table public.sp_todos enable row level security;
revoke all on public.sp_todos from anon, authenticated;
grant select, insert, update, delete on public.sp_todos to authenticated;
-- the same four "members read / insert / update / delete" policies as the food tables
create trigger sp_todos_touch before insert or update on public.sp_todos
  for each row execute function private.sp_touch();

-- Who completed a to-do is set by the database, never trusted from the client.
create function private.sp_todos_completion() returns trigger
language plpgsql security invoker set search_path = ''
as $$
begin
  if new.completed_at is not null and (tg_op = 'INSERT' or old.completed_at is null) then
    new.completed_at := now();
    new.completed_by := (select auth.uid());
  elsif new.completed_at is not null then
    new.completed_at := old.completed_at;  -- already done: keep the original time and person
    new.completed_by := old.completed_by;
  else
    new.completed_by := null;
  end if;
  return new;
end;
$$;
create trigger sp_todos_completion before insert or update on public.sp_todos
  for each row execute function private.sp_todos_completion();

alter table public.sp_todos replica identity full;
alter publication supabase_realtime add table public.sp_todos;
```

The insert branch matters for undo: `restoreTodo` reinserts a completed row, and the trigger stamps it with the restoring person and time. That is acceptable; keeping the original values would mean trusting the client.

Policy tests in `supabase/tests/strandparken_policies.sql`: a member reads and writes their household's to-dos; a member of the other household sees 0 rows and updates 0 rows; a non-member sees 0 rows; `completed_by` is set to the caller even if the client sends another id; `owner = 'x'` is rejected. Apply the migration the way earlier Strandparken migrations were applied (see the roadmap), then regenerate the types.

## Acceptance criteria

- [ ] A to-do item has a title, an owner (Camilla, Jonas or Fælles), an optional due date, an optional note, `completed_at` and `completed_by`, and no recurrence.
- [ ] The quick-add field "Tilføj to-do" at the top adds a to-do on Enter; the owner defaults to Fælles until another owner is chosen.
- [ ] Tapping an item opens a bottom sheet to edit owner, due date and note.
- [ ] Filter chips: Camilla, Jonas, Fælles.
- [ ] Groups: "Snart" (with a due date, soonest first), "Når der er tid" (no due date), "Klaret" (collapsed, last 30 days).
- [ ] Overdue items show their date in a warning colour.
- [ ] Items are checked off directly in the list; swiping left deletes, with a "Fortryd" toast.
- [ ] Changes sync between both members' devices.
- [ ] The owner is shown as an avatar: C, J, or CJ for Fælles.
- [ ] To-dos are not shown on Hjem.

## Open questions

1. **Owner of a quick-added to-do when one chip is selected.** The source document says "Owner defaults to Fælles until another owner is chosen". Default: selecting exactly one chip counts as choosing that owner for new to-dos, and the chip row shows "Nye to-dos: Jonas" so the effect is visible. The alternative is always Fælles, with the owner changed in the sheet.
2. **Should a completed to-do be reopenable?** Default: yes. Unticking in "Klaret" clears `completed_at` and moves it back. The source document does not say otherwise.
